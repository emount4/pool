# Отчёт по проекту «Бассейн» и выполнению КР №2

**Дата:** 11 октября 2026 года.  
**Версия:** 2.0.0 с обновлением показа пароля.  
**Основа:** [emount4/pool](https://github.com/emount4/pool), исходный коммит `a6286ff`.  
**Предметная область:** управление клиентами и посещениями бассейна.  
**Основание проверки:** приложенное полное ТЗ КР №2, текущие исходники, сохранённые журналы тестирования и предоставленный Windows-лог.

## 1. Результат

В проекте реализован функционал всех 20 пунктов обязательного минимума: JavaFX-интерфейс, PostgreSQL через JDBC, таблицы, CRUD, связанные данные, поиск, фильтры, сортировка, валидация, сообщения об ошибках, FXML, CSS, разделение слоёв, статистика и экспорт.

Полное выполнение всего ТЗ пока требует подтверждения трёх практических пунктов:

1. Подключение именно к сохранённой базе КР №1 либо её перенесённой копии с прежними данными.
2. Развёртывание готового преподавательского примера с backend и web-интерфейсом через Docker.
3. Ручная демонстрация основных операций и изменения размера окна на компьютере команды.

Наличие функции в исходниках и успешный автоматический тест не означают, что весь сценарий уже показан на Windows. В отчёте эти виды подтверждения разделены. Новый прогон тестов при составлении отчёта не выполнялся; использованы сохранённые результаты последнего обновления.

## 2. Назначение приложения

Приложение позволяет сотруднику бассейна вести список клиентов, планировать посещения, выбирать свободное время и дорожку, отменять записи, просматривать историю, получать статистику и выгружать данные.

Переход от КР №1 к КР №2 выполнен через добавление графического интерфейса к существующей предметной области и слоям работы с данными. Прежний консольный интерфейс сохранён отдельно в `ConsoleMain`. Обычные скрипты запуска открывают JavaFX-приложение через `Main` и `PoolApplication`.

| Роль | Доступные возможности |
| --- | --- |
| Оператор | Клиенты, посещения, поиск, фильтрация, сортировка, статистика и экспорт |
| Администратор | Возможности оператора и управление пользователями |

Раздел пользователей скрыт у оператора. Сервис управления пользователями дополнительно проверяет роль, поэтому ограничение не сводится к скрытию вкладки.

## 4. Архитектура

Основной путь выполнения операции:

**FXML → Controller → Service → Repository → JDBC → PostgreSQL.**

| Слой | Основные файлы и пакеты | Ответственность |
| --- | --- | --- |
| Запуск | `Main`, `PoolApplication` | Запуск JavaFX, создание окна, смена экрана входа и главного экрана |
| Представление | `src/main/resources/fxml`, `css/pool.css` | Разметка экранов и визуальное оформление |
| Контроллеры | `presentation/fx/controller` | Получение действий пользователя, открытие форм, обновление интерфейса |
| Сервисы | `application/service` | Бизнес-правила, валидация, фильтрация и статистика |
| Авторизация | `application/auth`, `application/security` | Вход, сессия, начальный администратор и правила пароля |
| Модель | `domain/model` | Клиент, посещение, пользователь, роли и статусы |
| Контракты хранения | `domain/repository` | Интерфейсы репозиториев |
| Доступ к БД | `infrastructure/database` | JDBC-соединения, SQL, чтение и запись |
| Экспорт | `infrastructure/export/TableExporter` | CSV и XLSX |
| Вспомогательные компоненты UI | `FxTasks`, `Ui`, `Views`, `Labels` | Фоновые задачи, сообщения, загрузка FXML и отображение значений |

SQL не размещён в обработчиках кнопок. Контроллеры вызывают сервисы, а репозитории выполняют операции хранения.

Данные таблиц хранятся в `ObservableList`. `FilteredList` задаёт текущий набор строк, а `SortedList` связан с компаратором `TableView`. После изменения данных `MainController.reload()` повторно читает данные и обновляет коллекции через `setAll`.

Обращения к БД и запись файлов выполняются через `FxTasks` вне JavaFX Application Thread. Результат задачи применяется в интерфейсе. Это позволяет не блокировать окно во время SQL-запроса или экспорта.

## 5. База данных

Сохранены основные таблицы исходного проекта.

| Таблица | Основные поля | Назначение |
| --- | --- | --- |
| `clients` | `id`, `first_name`, `last_name`, `phone`, `email`, `birth_date` | Данные клиентов |
| `visits` | `id`, `client_id`, `visit_date`, `start_time`, `duration_minutes`, `lane_number`, `status`, `created_by` | Расписание и история посещений |
| `system_users` | `id`, `username`, `password_hash`, `role`, `active`, `created_at` | Учётные записи сотрудников |

Связи:

- `visits.client_id` ссылается на `clients.id`.
- `visits.created_by` ссылается на `system_users.id`.
- Один клиент может иметь несколько посещений.
- Клиента с существующими посещениями удалить нельзя.

Схема содержит первичные и внешние ключи, уникальные телефон, email и логин, ограничения ролей, статусов и диапазонов. Индексы добавлены для клиента, даты и статуса посещения.

| SQL-файл | Назначение |
| --- | --- |
| `database/schema.sql` | Создание таблиц в пустой базе |
| `database/data.sql` | Учебные данные: 8 клиентов, 20 посещений, 2 пользователя |
| `database/migrations/002_no_overlaps.sql` | Расширение `btree_gist` и ограничения пересечений расписания |

Миграция добавляет два EXCLUDE-ограничения: занятость одного клиента и одной дорожки. Отменённые посещения не блокируют расписание. Соседние интервалы разрешены. Если старые данные уже содержат пересечения, их необходимо исправить перед применением миграции.

### Подключение к базе КР №1

Совместимость со структурой прежнего проекта реализована. Однако запуск новой базы с учебными данными сам по себе не подтверждает использование сохранённой базы КР №1.

Для работы с прежней базой необходимо указать её адрес, имя, пользователя и пароль во внешнем `database.properties`, затем запустить клиент через `run.bat`. Запускать `schema.sql` и `data.sql` поверх прежней базы не нужно. Если база переносилась в Docker, требуется проверить сохранность данных и использование правильного тома.

Приоритет конфигурации:

1. `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`.
2. Внешний `database.properties`.
3. Встроенный `src/main/resources/database.properties`.

Дополнительно поддерживаются `db.schema` и JVM-свойство `-Dpool.config=путь`. Пароль базы задаётся в конфигурации или окружении; в Java-классах он не прописан.

## 6. Графический интерфейс

| FXML-файл | Назначение |
| --- | --- |
| `login.fxml` | Вход, повторное подключение и создание первого администратора при пустой таблице пользователей |
| `main.fxml` | Главное окно с вкладками и строкой состояния |
| `clients.fxml` | Таблица клиентов, действия, поиск и фильтры |
| `visits.fxml` | Таблица посещений, действия, поиск и фильтры |
| `statistics.fxml` | Показатели, период и диаграмма |
| `users.fxml` | Управление пользователями для администратора |
| `client-form.fxml` | Добавление и редактирование клиента |
| `visit-form.fxml` | Добавление и редактирование посещения |
| `user-form.fxml` | Добавление и редактирование пользователя |

FXML связан с контроллерами через `fx:controller`, поля — через `fx:id`, обработчики — через `onAction`. Основное оформление вынесено в `pool.css`.

На экране входа добавлена кнопка «Показать» / «Скрыть». Значение синхронизируется между `PasswordField` и видимым `TextField`. Переключение сохраняет введённый текст, очистка очищает обе версии поля. Эта функция проверена отдельным UI-тестом.

## 7. Реализованные функции

### Клиенты

- Просмотр клиентов в таблице.
- Создание и редактирование через отдельную форму.
- Удаление с подтверждением и проверкой связанных посещений.
- Поиск по имени, фамилии, телефону и email.
- Фильтрация по возрасту и наличию email.
- Сортировка по столбцам.
- Переход к посещениям выбранного клиента.
- Экспорт текущих строк.

### Посещения

- Просмотр расписания и истории.
- Создание, редактирование и удаление.
- Отмена будущего запланированного посещения.
- Выбор клиента из списка вместо ручного ввода внешнего ключа.
- Поиск свободных интервалов и дорожек.
- Просмотр данных клиента выбранного посещения.
- Поиск по данным клиента.
- Совместные фильтры по статусу, дорожке, клиенту и периоду.
- Сортировка, в том числе по дате и времени.
- Обновление данных и актуализация статусов.
- Экспорт отфильтрованных строк в текущем порядке.

Статусы: `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`. Актуализация выполняется при загрузке главного окна и обновлении. Постоянный автоматический таймер не реализован.

### Пользователи

Администратор создаёт пользователей, меняет логин, роль и пароль, блокирует доступ. Реализована защита от блокировки себя и удаления последнего активного администратора через изменения учётных записей. Пароли хранятся как PBKDF2-хеши.

### Поиск и сортировка

Поиск использует несколько смысловых полей. Фильтры применяются совместно. Даты периода подтверждаются кнопкой применения; неверный период показывает ошибку. Сброс очищает фильтры.

Сортировка выполняется по заголовкам `TableView`. Для сортировки по нескольким столбцам используется `Shift` + щелчок. `SortedList` связан с компаратором таблицы; даты и числа сравниваются в соответствующих типах.

## 8. Валидация и бизнес-правила

| Объект | Правила |
| --- | --- |
| Имя и фамилия | Обязательны, 2–100 символов |
| Телефон | Обязателен, 7–15 цифр; форматирование нормализуется |
| Email | Необязателен, корректный формат, до 255 символов |
| Дата рождения | Обязательна, не в будущем, возраст не более 120 лет |
| Контакты | Телефон и указанный email уникальны |
| Клиент посещения | Должен существовать |
| Работа бассейна | С 07:00 до 22:00 |
| Длительность | 30–180 минут, кратна 30 |
| Время начала | Шаг 30 минут |
| Дорожка | От 1 до 8 |
| Новая запись | Не допускается в прошлом |
| Пересечения | Один клиент и одна дорожка не могут одновременно занимать пересекающиеся интервалы |
| Редактирование и отмена | Для ещё не начавшегося запланированного посещения |
| Удаление клиента | Запрещено при наличии посещений |
| Учётные записи | Проверяются роль, пароль и сохранение активного администратора |

Формы показывают ошибки до успешного сохранения. Сервисные проверки дополняются ограничениями PostgreSQL.

## 9. Обработка ошибок

`Ui.message` переводит ошибки приложения и SQLState в понятные сообщения. Например:

| Ситуация | Обратная связь |
| --- | --- |
| Дубликат контакта или логина | Предложение изменить уже используемое значение |
| Связанная или удалённая запись | Предложение проверить связанные данные и обновить список |
| Пересечение интервалов | Сообщение о занятом времени или дорожке |
| Нарушение ограничений базы | Предложение проверить длины, даты и числа |
| Нет подключения | Предложение проверить PostgreSQL и параметры подключения |
| Нет таблиц | Указание на необходимость инициализации базы |
| Ошибка экспорта | Предложение проверить права на папку и закрыть файл в Excel |

Ожидаемые ошибки показываются в форме или диалоге. Неожиданные ошибки журналируются; пользователю не выводится stack trace вместо интерфейса. Журнал приложения — `pool-desktop.log` рядом с файлами запуска.

## 10. Статистика

Отдельная вкладка содержит девять показателей.

| № | Показатель | Расчёт |
| --- | --- | --- |
| 1 | Клиентов в базе | Количество всех загруженных клиентов |
| 2 | Посещений за период | Число посещений после ограничения выбранным периодом |
| 3 | Посещений сегодня | Число посещений текущей даты в выбранном наборе |
| 4 | Запланированных | Количество `PLANNED` |
| 5 | Идущих сейчас | Количество `IN_PROGRESS` |
| 6 | Завершённых | Количество `COMPLETED` |
| 7 | Отменённых | Количество `CANCELLED` |
| 8 | Средняя длительность | Среднее `duration_minutes` выбранного набора; 0 для пустого набора |
| 9 | Популярная дорожка | Дорожка с наибольшим числом посещений; при равенстве выбирается меньший номер; для пустого набора — прочерк |

Количество клиентов не ограничивается периодом посещений. Средняя длительность и популярная дорожка в текущем расчёте учитывают также отменённые посещения. Диаграмма по дорожкам исключает отменённые посещения. Это фактические правила текущей реализации, которые следует объяснить при демонстрации.

Статистика экспортируется вместе с обозначением выбранного периода.

## 11. Экспорт

Реализованы CSV и XLSX. Пользователь выбирает файл через `FileChooser`. Контроллер передаёт в `TableExporter` текущий набор строк таблицы, поэтому сохраняются фильтрация и порядок сортировки.

CSV записывается в UTF-8 с BOM, разделителем `;` и экранированием кавычек. Для значений с началом, похожим на формулу, добавляется защитный апостроф. XLSX формируется через Apache POI: заголовок выделен, первая строка закреплена, добавлен автофильтр.

Запись выполняется через временный файл с последующей заменой целевого файла. Операция идёт в фоновой задаче. После сохранения приложение сообщает путь и число строк.

## 12. Запуск на Windows

На компьютере пользователя подтверждены JDK 21 и работа Docker. Порт `5433` занят локальным процессом PostgreSQL. Для контейнера выбран `15433`.

### Проверка окружения

```powershell
java -version
javac -version
docker --version
docker compose version
docker info --format '{{.ServerVersion}}'
```

### Согласованные настройки

В `.env`:

```dotenv
POSTGRES_PORT=15433
POSTGRES_PASSWORD=postgres
```

Во внешнем `database.properties` для новой учебной базы:

```properties
db.url=jdbc:postgresql://localhost:15433/pool_db
db.username=postgres
db.password=postgres
```

Это пример конфигурации учебной базы; для прежней базы КР №1 используются её реальные реквизиты. При изменении `.env` пароль в уже созданном томе PostgreSQL автоматически не меняется.

### Запуск готовой поставки

```powershell
cd C:\Users\User\Desktop\pool-desktop
.\start.bat
```

`start.bat` запускает PostgreSQL через Compose, ожидает готовности и вызывает клиент. Если база уже работает или используется прежний локальный сервер:

```powershell
.\run.bat
```

Учебные аккаунты новой базы:

| Роль | Логин | Пароль |
| --- | --- | --- |
| Администратор | `admin` | `Admin123` |
| Оператор | `operator1` | `Operator123` |

В прежней базе сохраняются её пользователи и пароли. Учётные данные преподавательского примера относятся к другой системе.

### Сборка и запуск исходников

```powershell
.\mvnw.cmd clean verify
.\mvnw.cmd javafx:run
.\mvnw.cmd -Pportable clean package
```

`javafx:run` запускает исходники через Maven. `run.bat` использует уже собранный JAR из `app`; после изменения кода поставку необходимо пересобрать, чтобы этот JAR содержал изменения.

## 13. Docker и поставка

`compose.yaml` содержит сервис базы `postgres:16-alpine`, healthcheck, публикацию порта только на `127.0.0.1` и постоянный том. При первом создании базы выполняются SQL-схема, учебные данные и миграция.

```powershell
docker compose up -d --wait db
docker compose ps
docker compose exec db pg_isready -U postgres -d pool_db
docker compose down
```

Обычный `down` сохраняет том. Команда `down -v` удаляет том и не подходит для сохранения прежних данных.

JavaFX запускается на компьютере, PostgreSQL — в Docker. `Dockerfile` предназначен для сборки артефактов, а не для запуска графического окна.

Готовая поставка включает исходники, Maven Wrapper, SQL, документацию, JAR, JavaFX-библиотеки и скрипты. Подготовлены библиотеки Windows x64, Linux x64, macOS Intel и Apple Silicon. Java 21 и Docker устанавливаются отдельно. Поставка не является нативным EXE-инсталлятором с включённым Java runtime.

### 21.7. Пример связи файлов

При сохранении клиента участвуют следующие компоненты:

1. `client-form.fxml` определяет поля и кнопку сохранения.
2. `ClientFormController` получает введённые значения.
3. `ClientService` проверяет поля и уникальность контактов.
4. Контракт `ClientRepository` определяет операцию хранения.
5. `JdbcClientRepository` выполняет SQL через соединение `DatabaseManager`.
6. PostgreSQL сохраняет строку в `clients`.
7. После успешной операции главное окно повторно загружает данные, и таблица обновляется.

При объяснении проекта удобно показывать этот путь по файлам: он демонстрирует, зачем нужны отдельные слои и почему код кнопки не содержит SQL.
